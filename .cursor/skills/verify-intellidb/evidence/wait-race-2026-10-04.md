# Wait spinner clears before history replay on first chat open (2026-10-04)

## Symptom

First chat selection after app open: spinner appears briefly, clears in
milliseconds, messages only arrive seconds later via `onActivity`. Second chat
selection behaves correctly (spinner spans the whole load).

## Repro probe

`wait-race-probe-2026-10-04.ts` drives the real `src/lib/AgentHost.ensureAgent`
with bun. Scenario A mimics React StrictMode's mount pattern (ChatView's
`handleAgentConnect` effect fires twice on first mount, so two concurrent
`agent:connect` IPC calls hit `ensureAgent` for the same chatId). Scenario B is
the chat-switch control (one connect).

Failing output (chat 11 "hey", stored session, real agent binary):

```
=== A: two concurrent ensureAgent calls (StrictMode mount pattern) ===
Existing agent found, returning session ID
+0.03s [A2] resolved sessionId=''
+4.64s [A1] activity kind=user "hey"
...replay...
+4.68s [A1] resolved sessionId='faefd9aa-37d2-4fc5-9c06-0119af243c5d'

=== B: single ensureAgent call (chat-switch pattern, control) ===
+10.50s [B1] activity kind=user "hey"
...replay...
+10.52s [B1] resolved sessionId='faefd9aa-37d2-4fc5-9c06-0119af243c5d'
```

## Root cause

`startAgent` synchronously plants `agents.set(chatId, { client: undefined,
ready: false })` before spawning. A concurrent `ensureAgent` for the same
chatId hits the `existing` early-return and resolves instantly with `''`. The
renderer clears `waitForInitialActivity` on that resolution, so the spinner
dies at 30 ms while the real load takes ~4.6 s. `cursor-agent` delivers the
history replay before the `session/load` response, which is why a single
connect (scenario B) behaves correctly and only the first mount
(StrictMode double-invoke, dev build) shows the race. The early-return is a
genuine race for any concurrent connect, not just StrictMode.

## Fix

Serialize `ensureAgent` per chatId with an in-flight promise map instead of
trusting the placeholder entry.
